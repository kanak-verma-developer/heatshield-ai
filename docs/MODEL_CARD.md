# Model Card — HeatRiskModel v1.2

## Task
Regression: predict a 0–100 urban heat-risk score for a zone from
environmental/geospatial features.

## Training data
- **Source:** `data/training_data.csv`, generated by `ml/generate_dataset.py`.
- **Status: SYNTHETIC.** Not real Moradabad sensor or satellite data.
- 24,090 rows: 11 zones × 365 simulated days × 6 samples/day (every 4 h) —
  one full seasonal cycle.
- Target (`heat_risk_score`) = `risk_formula(...)` (a weighted combination of
  surface temperature, built-up density, vegetation, humidity and road
  density) **plus Gaussian noise (σ = 3.5)**. The same inputs are then given
  to the model, so the model is asked to *re-discover a formula we wrote*.

## Features
`air_temp, surface_temp, humidity, wind_speed, ndvi, built_up_density, road_density, water_proximity`

## Split methodology
Time-aware split: the last 20% of days (19,272 train / 4,818 test rows) are
held out. Because the seasonal cycle is one year long, the test period is a
different part of the season than most of the training data, which is a
mildly harder test than a random split. 3-fold CV is used inside
`RandomizedSearchCV` (12 candidates per algorithm) on the training portion.

## What R² means here — and what it does not
- **Noise ceiling:** applying the *exact* data-generating formula to the test
  targets gives R² = **0.8805** (`synthetic_noise_ceiling_r2` in the metadata).
  The selected model scores 0.8801 — i.e. it has recovered the formula almost
  perfectly, and cannot do better because the rest is the noise we injected.
- A linear model winning is the same fact seen from another side: the
  synthetic target is nearly linear in the inputs.
- Therefore **R² ≈ 0.88 is not "88% accuracy" and says nothing about
  real-world performance in Moradabad.** It is a pipeline sanity check
  (the training/evaluation code works and recovers a known relationship).
- A test in `tests/test_model.py` asserts the model's R² cannot exceed the
  ceiling by more than 0.01 (a leakage alarm).

## Feature importance / explanations
- `feature_importance` (global) for a linear winner is the absolute
  standardized coefficient, normalized to sum to 1 (`importance_method` in
  the metadata). It is an *estimate of how the model weights inputs*, not a
  causal measurement. `surface_temp` dominates partly because it is itself a
  deterministic function of the other inputs in this synthetic setup.
- **Per-zone explanations** (`/api/zones/{id}`) are computed by
  counterfactual re-prediction: each zone attribute is replaced by the
  city-mean prior (with surface temperature recomputed) and the change in
  predicted risk is reported in risk points. This is model-specific and
  works for any algorithm, but it inherits the model's assumptions.

## Known limitations
1. **Synthetic data only.** Real-world accuracy is unverified until real
   IMD / Sentinel-2 / NASA POWER data replaces it (same column schema).
2. **Zone land-cover values are hand-set priors** (`data/zones.py`), unverified,
   and fixed in time. They determine most of the zone ranking and therefore the
   hotspot list.
3. In live mode, `surface_temp` is *computed* from air temperature and the
   priors with the same formula used to build the training data — it is not a
   measured land-surface temperature.
4. No spatial autocorrelation; rows are treated independently.
5. Forecast = the same model run on Open-Meteo's hourly weather forecast (or a
   trend/diurnal extrapolation when offline). The ± band is `RMSE × (1 + 0.15·h)`
   using the synthetic-data RMSE, so it is illustrative, not a calibrated
   prediction interval.
6. No SHAP; no calibration against real heat-illness or temperature outcomes.

## Versioning
Every training run writes `backend/models/model_metadata.json`: version,
algorithm, hyperparameters, scikit-learn version, timestamp, dataset
description and row counts, split method, features, metrics for all
candidates, the noise ceiling and the importance method. The pickled model
must be loaded with the same scikit-learn version it was trained with; the
backend warns at start-up if they differ.
